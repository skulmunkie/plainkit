`mountApp(container, config)` in `js/app.js`, step 4 of the app framework, owns all the chrome of an app so a consumer writes a config and modules and no bar, menu, search, footer or focus handling. It builds the header (one hamburger, the brand, the header search and the settings menu with the theme switch), the side navigation, breadcrumbs (`App > Module > the route labels`), the footer, skip links, landmarks, an empty toast stack and dialog host for the coming services, hash routing `#/<moduleId>/...`, and the module host with its loading, error, forbidden and not-found states. The default `layout: 'side'` lists the modules as the top-level sections of the side nav, the active module holding its own nav; `layout: 'top'` puts the module links in the bar for a tiny app. A narrow screen has one drawer either way. Route changes move focus to the page heading, announce "Title, page loaded", update the document title and close the drawer; the theme is kept in the store (`?theme=` wins for one visit); the header search asks the active module (`search(query, ctx)`), else its nav; hovering a module link warms its chunk. The module nav is structure (a few stable destinations): a record route sits under its list in the route tree (`children`, `label`), so the list entry stays current and the trail reads `Demo app > Orders > Order 8`; a nav over 12 top-level or 40 entries is logged with that advice. The config is checked when mounted (a bad value throws, an unknown key is one warning). A runnable demo is in `samples/app/` (`index.html`, and `top.html` for the top layout). Nothing changes for Blazor yet (`PkApp` is a later step). Reference: `references/app.md` in the skills.
