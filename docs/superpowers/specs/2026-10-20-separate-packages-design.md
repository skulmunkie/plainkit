# Separate packages for the larger components: requirements and design (refs #1656)

Status: r3, owner answers of 2026-10-20 applied (decided items are marked DECIDED in section 14; the rest keep their recommendation). Revised after the owner correction that npm is not a distribution channel (the units are GitHub Pages, GitHub release zips and the one NuGet package). Research and design only; no product code, no ceiling change. Owner direction 2026-10-20: carve out separate packages for the bigger
components so the core package stays small; the npm ceilings were raised once (packed 883,500 to 900,000, unpacked 3,282,700 to 3,350,000) as a stopgap. Related: #1644
(page size), #598 (pk-os), #430 canvas, #431 SVG toolkit, #432 dock, #1486 markdown editor; supersedes the 2026-10-11 packaging spec's "no sub-packages now" for the reasons in section 1.

Measured on `origin/main` (498c0539, version 0.19.0) after `npm ci` and `node scripts/bootstrap.mjs`: `npm pack --dry-run --json` in `core/`, gzip of each file in `core/dist`,
import-closure scripts over `core/dist` (static and literal dynamic imports). Sizes are gzip unless a column says raw. "Packed" estimates for a candidate are
its JS gzip + its slice of the generated metadata (`elements/api.json`, `custom-elements.json`, `web-types.json`, the editor files) + half of its skill reference text (the other half is in the Blazor
skill, which the npm package already leaves out); they are estimates (the tarball compresses across files), to be replaced by measured values in each phase.

## 1. Evidence on main

- Tarball: 883,476 packed / 3,271,119 unpacked bytes, 352 files; ceilings 900,000 / 3,350,000 (`core/tests/package-size.test.mjs`). Headroom is 16.5 KB packed.
- **The runtime JS is not what fills the package.** By gzip of each file: element modules (134 files) 239 KB; skills (27 files, SDK skill only) 229 KB; CEM, web-types, `elements.d.ts`, VS Code data 178 KB;
  `dist/js` 152 KB; `elements/api.json` 118 KB; the audit CLI (`dist/tools`) 44 KB; CSS and icons 17 KB; `manifest.json` 16 KB. Metadata plus skills are about 59 percent of the packed bytes and grow
  with every element (average 2.2 KB of metadata and 1.7 KB of skill text per element, against 1.8 KB of JS). **A split that moves only JS saves less than half of what the element costs the tarball**: an extra
  must take its metadata and skill text with it (sections 5 and 7).
- **Already outside the package:** `dist/modules` (the dev tools, 69 KB gzip, 172 KB raw, own manifest and zip), `dist/gallery` (332 KB gzip), `manifest.extras.json` files, the Blazor skill, `api.full.json`. The precedent for a second unit exists
  (`docs/tool-modules.md`: "the two units"; modules import `../../js/*.js`, an import map remaps them when hosted apart).
- **Dead weight in the package today:** 33 files in `dist/js` (109 KB raw, 49 KB gzip) are reachable from no element, `plainkit.js` or `js/app.js` by import analysis (`custom-sdk*`, `layout-*`, `theme-*-logic`,
  `console-logic`, `element-inspector*`, `framework-checks`, `quality`, `scoring`, `zip-store`, `mount-support` ...). Only the dev-tool modules import them, and the modules are not in the npm package. Phase 1 confirms each with an import-graph test before moving it.
- **Loader:** `core/js/loader.js` plans from tag names. In `dist` (`BY_NAME`) a tag `pk-x` imports `./x.js` next to the registry with no registry fetch (#1502); the registry (`dist/elements/registry.js`) is read only to word a failure ("check the spelling"). There is no
  way to point a tag at another package. `core/package.json` has `exports` (`./elements/*`, `./js/*`, `./css`, `./skills/*`, `./dist/*`), `sideEffects` for elements and CSS, and one `files` list with negations.
- **Release:** one version (`core/VERSION`), checked by `core/tools/versioning.mjs` (stamps `core/package.json`, `Directory.Build.props`, manifests; `check --tag`); `release.yml` jobs `verify` (full verify with `--pack --browser`),
  `build` (bootstrap, version/tag check, tests, `dotnet pack`, three zips) and `publish` (GitHub release, `dotnet nuget push --skip-duplicate`, `npm publish --provenance --access public` only when `NPM_TOKEN` is set). One npm package, one NuGet package.
- **Blazor:** `PlainKit.Blazor` ships a byte copy of `core/dist` as static web assets (`wwwroot/plainkit`, 5.4 MB on disk: gallery, skills, modules included), the generated `Pk*` wrappers (from `blazor/mappings/<name>.json`, 133 mappings) and the dev-tool
  components (`PkDevTools`, `PkThemeEditor`, `PkCodeExplorer`, `PkScorecard` ...) that import `plainkit/modules/<tool>/`. `scripts/check-package.mjs` asserts the nupkg's contents; `scripts/tests/blazor-wrapper.test.mjs` and `blazor/handwritten.json` police the hand-written files.
- **API baseline:** `core/tools/api-surface.mjs` lists classes, tokens, JS exports and every element's API in one file (`api.baseline.json`); a removed item needs a minor (while 0.x) bump. Every candidate below is in the 0.19 baseline (pk-dock 33 items, pk-canvas 41, pk-markdown-editor 59).
- **Planned growth** (all unbuilt, each design says "lazy layers, 3 to 6 KB gzip per module, never raise a limit"): canvas layers C2 to C5 (2.8 KB element now), the SVG toolkit (about 10 modules plus an editor and viewer, order of 25 to 40 KB gzip by the 10-19 spec's per-module
  estimates), dock floating layer, layout builder as a route, rich text phases 3 to 6, code explorer growth, pk-os. Without a split these alone consume the stopgap headroom (40 to 60 KB packed with their metadata and skills).

## 2. Goals and non-goals

Goals:

1. A typical app (forms, tables, pages, dialogs, app shell) takes one artifact (the core zip) whose packed size goes **down** from today and stays flat as extras grow.
2. A rarely needed, large component (canvas, SVG, dock, markdown, dev tools, pk-os later) is its own artifact (zip and Pages folder), added on purpose, with its **own metadata, types, CEM, skill text** (on the Blazor side the one package stays, with a declared set of extras, section 6).
3. Nothing is lost: same tags, same props, same events, same gallery and docs on the Pages site; per-element lazy loading is unchanged.
4. One version, one tag, one release: lockstep; a consumer never needs a compatibility matrix.
5. Every package has a size ceiling that only ratchets down, from its first publish. The core ceilings are lowered with each move (section 9).
6. Existing imports keep working for one deprecation window.

Non-goals: a package per element (the 2026-10-11 spec's 129-package matrix); raising any ceiling; a mandatory build step (the no-build path stays: unzip or copy, script tags, optional import map); splitting the CSS page layer or tokens;
independent versions per package; moving the Blazor assembly's core wrappers; third-party vendored code; designing pk-os, the SVG toolkit or the layout builder here (they only get a package to land in).

## 4. Proposed split

Owner direction (2026-10-20, corrected the same day): **we do not publish to npm and do not want to yet.** The distribution units today are GitHub Pages (`dist/` as a URL prefix, always latest `main`), the GitHub release of a version tag (the dist zip, the modules zip, their manifests, the skills zip, the `PlainKit.Blazor` nupkg) and NuGet (`PlainKit.Blazor`, the one published package; `PUBLISHING.md`). So a "package" in this spec is a **release artifact plus a Pages path**: a zip with its own manifest, metadata, types and skill text, and a folder on the Pages site. One artifact per extra (core, canvas, svg, and so on), each with an explicit declaration of the JS modules a consumer uses; on the Blazor side **one NuGet package**, `PlainKit.Blazor`, where the project declares core plus the extras it wants, or full (section 6). All lockstep (section 8).

Artifact ids (dotted, no registry scope to own; DECIDED): `plainkit` (core), `plainkit.tools`, `plainkit.canvas`, `plainkit.dock`, `plainkit.markdown`, later `plainkit.svg`, `plainkit.os`. The id names the zip (`<id>-<version>.zip`, for core `plainkit-<v>.zip`), the Pages folder (`packages/<id>/`) and the manifest.

| Artifact id | Takes | Requires | Blazor option name |
| --- | --- | --- | --- |

**Two first-class shapes (owner clarification 2026-10-20).** (1) **FULL**: everything in one artifact, `plainkit-dist` (the all-in-one zip and the Pages `dist/` prefix); what any ordinary consumer just uses, and the docs lead with it. (2) **CORE + MODULES**: `plainkit` plus any of `plainkit.tools`, `plainkit.canvas`, `plainkit.dock`, `plainkit.markdown`, `plainkit.audit` for consumers who want it lean. FULL is not a deprecated path or a back-compat shim; it is permanent, generated from the same `packages.json` (its content is the union), and a test keeps the union of core and all modules equal to it.

**Audit module (`plainkit.audit`, DECIDED: separate from core).** The CLI is plain Node ESM with no browser-runtime dependency. Without npm it is run from files: unzip `plainkit.audit-<v>.zip` (or take the Pages folder `packages/plainkit.audit/`, or use the FULL zip, which contains it) and run `node plainkit.audit/audit.mjs <path>`. A Pages-hosted single-file build (`packages/plainkit.audit/audit.mjs`, no imports outside its folder) allows `curl -O` then `node audit.mjs`, so CI needs no checkout. The folder's generated `package.json` keeps `bin` so a later npm publish and `npx` would work unchanged. What stays in core: the rule documentation and ids the skills quote, a `plainkit audit` stub that prints the two ways to get the module, and the `registry.extras` map the audit uses to say "pk-dock needs plainkit.dock". The audit moves in a later wave, after the four element/tool artifacts; the Blazor skill's `npx plainkit audit` text is rewritten to the file-based command in that same phase.

Why one artifact per extra: one `extras` bundle would put a 70 KB markdown reader behind a 200 KB editor family, and an extra grows (SVG, layers) without touching the others. Why not one per element: the 129-package matrix of the 2026-10-11 spec; the unit is a family with a size and an audience (rule in section 3), and a small element joins its family (property-grid rides with canvas, Q11). Each artifact costs one manifest, one pack check and a few release steps (section 8), so the rule of section 3 keeps the count near six.

**Source layout does not move.** Sources stay in `core/{elements,components,pages,shells,modules}/<name>/`; tests, tier rules (C1 to C4), the gallery and the site keep working unchanged. A new field in the element's meta, `"package": "dock"` (absent means core), and a repository-level `packages.json` (id, folders and `js/` files it owns, requires, NuGet option name, ceilings) are the single declaration. The build, the version check, `check-package.mjs`, `release.yml`, `build-pages.mjs` and the size test all read `packages.json`; none hard-codes an id.
A new tier rule P1 (a node test, like `core/tests/tiers.test.mjs`): code in core may not import a file owned by an extra; an extra may import core and its declared requirement only. The `dist/js` helper files get an owner in `packages.json` by prefix (`dock-*`, `markdown/`, `svg-*`, ...) or by explicit list.

`core/dist` stays the **full overlay tree** (everything, as now; the site, the gallery, Pages `dist/`, the Blazor `wwwroot/plainkit` copy, the dist zip and the tests keep reading it). The per-artifact folders are **assembled** from it: the build copies each id's files into `core/dist-packages/<id>/` (gitignored, added to `scripts/generated.mjs`) with its own filtered metadata, `manifest.json` and `importmap.json`, and zips each folder. Each folder uses the same relative layout as `dist` (`elements/dock.js`, `js/dock-model.js`, `skills/plainkit.dock/`), so unzipping an extra over the core folder reproduces the full tree. The generated metadata files are single files holding every element, so they are produced once per artifact, filtered.

## 5. How a consumer loads an extra

Principles: nothing eager; the extra costs a tag-to-URL map until a tag is used; per-element lazy loading stays; the failure when an extra is missing says which artifact to add; no build step and no registry required.

**Registration.** Each extra ships `register.js` (tiny, side-effect): it calls `registerExtra('plainkit.dock', { 'pk-dock': './elements/dock.js', ... }, import.meta.url)` from a new `js/extras.js` in core (about 0.3 KB gzip, within the loader's budget). `extras.js` holds a `Map` tag to absolute URL, derived from the extra's own location, so it works from any host. `loadElements` checks the extras map before the by-name path (`./x.js` beside the registry), and `registerExtra` itself re-runs `loadElements(document)` so tags already on the page upgrade whatever the script order. Nothing in the extras loads until its tag appears (`observeElements` covers later additions as today).

**The three ways a plain-HTML page gets an extra** (all produce the same result; the choice is only where the files live):

1. *Pages prefix, latest `main`* (prototypes, the gallery): core as today, `<script type="module" src="https://<pages>/plainkit/dist/plainkit.js">`; an extra adds `<script type="module" src="https://<pages>/plainkit/packages/dock/register.js">`. Always the latest `main`, never pinned (Pages serves one deployment). The existing `dist/` URL keeps serving the full overlay, so every current link works unchanged and already contains every extra's files (tags need no `register.js` there: the by-name path finds them).
2. *Unzipped release folder, pinned* (production): `plainkit-<v>.zip` unzipped into `vendor/plainkit/`, then each wanted `<id>-<v>.zip` unzipped **over the same folder** (the modules zip's documented pattern: "unzip it into the runtime folder"). The files land beside core, the by-name path finds `./dock.js`, and `register.js` is optional. Or just the one all-in-one `plainkit-dist-<v>.zip`. Pinning is the release version in the folder name; the zips are hosted by the consumer.
3. *Side by side* (extra hosted apart from core, for example core from Pages and one pinned extra from your server): the extra's files import core by relative path (`../js/element.js`), exactly like the modules today (`docs/tool-modules.md`). The artifact's generated `importmap.json` is one `<script type="importmap">` snippet that remaps the resolved core URLs to wherever core is hosted (an import map matches the resolved URL, so no rewrite of the files is needed); the `plainkit-runtime` meta tag, already used for the modules, names the base. No bundler and no node_modules.

**Versioned and latest forms.** Latest: the Pages `packages/<id>/` path (and `dist/`). Pinned: the release zip of that tag, unzipped by the consumer, or the GitHub release asset URL for tooling that downloads it. There is no CDN by tag (PUBLISHING.md: the tag does not carry `dist`) and this spec does not add one; whether Pages should also keep `v/<version>/` folders is Q18. `register.js` checks the extra's stamped version against core's `version.js` and warns once on a mismatch (a pinned extra next to a latest core is the failure this catches).

**Integrity.** Each artifact has its own `manifest.json` (SRI hash per file, `requires: plainkit <version>`, as `dist/modules/manifest.json` does today) attached to the release as `<id>-manifest-<version>.json`, and the zip holds it. A consumer verifies the unzipped folder with the existing manifest tooling, or pins `integrity=` on the script tags from it. `dist-manifest.json` and `dist-manifest.extras.json` stay and list every file of every artifact once.

**Shared modules stay singletons.** An extra's elements import core helpers (`element.js`, `log.js`, `positioning.js` ...) by the same relative path core uses. In forms 1 and 2 they resolve to the one core copy by construction; in form 3 the import map makes them resolve to it. A browser case asserts identity in all three: the `Base` class an extra's element extends is the instance core created (`customElements` upgrade works, `log` is one logger).

**How the loader resolves an element from another artifact.** The registry file (`dist/elements/registry.js`) is read only to word a failure and keeps that role; it gains `export const extras = { 'pk-dock': 'plainkit.dock', ... }` generated from `packages.json`. Resolution order for `<pk-dock>`: (1) the `registerExtra` map (an explicit URL), (2) the by-name path beside the registry (works in the overlay and on Pages `dist/`), (3) failure. A `<pk-dock>` that resolves to neither logs once: "<pk-dock> is in plainkit.dock (not loaded): add its register.js (or unzip plainkit.dock-<v>.zip over the runtime folder; Blazor: add dock to PlainKitExtras)". The typo message stays for unknown tags. The tag stays inert (as any unknown element), nothing throws.

**Per-artifact metadata and types.** Each artifact has its own `custom-elements.json`, `web-types.json`, `vscode.html-custom-data.json`, `elements.d.ts`, `elements.vue.d.ts`, `elements/api.json`, `manifest.json` and `skills/`. Core's files list core's elements only, so tooling sees an extra's elements exactly when its folder is in the project (an editor setting or tsconfig `include` points at the folder). `elements.d.ts` in an extra augments `HTMLElementTagNameMap`, which merges. A future npm publish of the same folders (optional, unused; Q1) would need only a generated `package.json` and an `exports` map: the assembled layout is the package layout.

**Tools artifact.** Not elements: modules (`mountThemeEditor` and friends). It is today's modules zip, served at `modules/` beside core; `loadChunk` is unaffected. Hosting apart keeps working through the existing import-map and `plainkit-runtime` meta tag.

## 6. Blazor: one package, a declared set of extras

One NuGet package, `PlainKit.Blazor`, as today (owner direction: the efficient shape). It keeps every generated `Pk*` wrapper (133 mappings; the wrappers are a few KB of IL and the trimmer drops what a WebAssembly app does not use), so no assembly splits and no namespace changes. What the consumer chooses is
**which JS modules and static web assets follow the app**, and the choice is explicit.

**Declaration.** Two equivalent forms, one source of truth read by build and startup:

- `.csproj`: `<PlainKitExtras>canvas;dock;markdown</PlainKitExtras>` (or `<PlainKitExtras>full</PlainKitExtras>`; **absent means FULL, permanently**: one NuGet package whose default registration is everything; core + modules is an explicit choice made by listing modules). MSBuild exposes it to the compiler (`CompilerVisibleProperty`) and writes it to a generated `plainkit.extras.json` static asset, so the browser side reads the same list.
- Code: `services.AddPlainKit(o => o.Extras.Add(PkExtra.Canvas, PkExtra.Dock))` or `o.Extras.AddAll()`. A mismatch with the csproj list (code names an extra the csproj does not) is a startup error, not a merge: one declaration wins, the other must agree. The csproj is the recommended place (it drives the assets); the code form is for tests and hosts that publish without MSBuild assets.

**Static web assets follow the declaration.** The package ships the full tree under `_content/PlainKit.Blazor/plainkit/`, but a `buildTransitive` target (`PlainKit.Blazor.targets`, which already ships) removes the static web asset items of every extra not declared (patterns from a generated
`plainkit.extras.map`: extra to files, from `packages.json`) before the endpoints are built. A published app that chose core + modules contains core plus the declared extras only (FULL contains everything); `dotnet publish` of a core-only app drops the dock, canvas, markdown, tools and gallery/skills assets. The tools unit (`modules/`) is the `tools` extra; `gallery`
and `skills` are never served by default (they are design-time; `<PlainKitExtras>gallery</PlainKitExtras>` opts in for the dev tools that need them).
**JS modules follow the same list.** `PkRuntime.InitAsync` hands the declared list to the bridge, which calls `registerExtra` (section 5) for each from its `_content` URL, so an extra's tags load lazily, one element at a time, only when they appear. Nothing undeclared is registered.

**Two first-class registrations (owner clarification).** `AddPlainKit()` with no declaration registers FULL and serves every asset, forever; `AddPlainKit(o => o.Extras.Add(...))` and `<PlainKitExtras>canvas;dock</PlainKitExtras>` choose core + named modules, where the project-file declaration of the JS modules stays explicit. The diagnostics below apply only to projects that chose core + modules.

**An undeclared component is never silent.** Every generated wrapper carries `[PkRequiresExtra("dock")]` (from the mapping's `package`). Three layers, from earliest:

1. *Build time:* a Roslyn analyzer shipped in the package (`analyzers/dotnet/cs`) reports `PKB001` (only for projects that chose core + modules; warning by default, error with `<PlainKitStrictExtras>true</PlainKitStrictExtras>`, which the sample and templates set) for any use of a type with `[PkRequiresExtra]` whose extra is not in `PlainKitExtras`, in C# and in Razor markup (`<PkDock>`). The message names the fix: "PkDock needs the 'dock' extra: add dock to <PlainKitExtras> in the project file".
2. *Startup:* `AddPlainKit` validates the csproj list and the code list against the known extras (unknown name: error listing valid names); `PkRuntime.EnsureInitializedAsync` logs the declared set once at Information and, in Development, throws on a declaration the assets do not back (the target removed the files).
3. *Render time:* a wrapper whose extra is undeclared throws `InvalidOperationException` with the same message in Development and logs an Error once per component type (ILogger and the SDK log, so the logs viewer and the dev tools show it) in Production, then renders an inert, visibly marked placeholder (the SDK loader also prints the "is in plainkit.dock" message of section 5). No path renders a blank component without a diagnostic.

Generator and checks. `scripts/generate-blazor.mjs` reads `package` from the element meta and emits the attribute, `PlainKit.Blazor.targets` additions (the asset removal, the `CompilerVisibleProperty`) and `plainkit.extras.map`. `publish-dist.mjs` stays one copy of `core/dist`. `check-package.mjs` gains: the map covers every file under the extras exactly once; every `Pk*` wrapper of an extra has the attribute; the analyzer is in the nupkg. Tests: a bUnit test per
layer of the diagnostic; an MSBuild integration test (`dotnet publish` of a tiny app per option set, asserting which files exist under `wwwroot/_content`); the Blazor browser harness runs the sample twice, core-only (an undeclared component yields the diagnostic, not a blank) and full. The sample app declares `full`.
`handwritten.json` and the wrapper test are unchanged: no new hand-written wrapper, only the generator and targets grow.

**Payload budget.** A Blazor app's cost is what the host serves: runtime assets (elements, js, CSS, icons) plus the declared extras. `packages.json` gets two numbers (`blazorPayload`), measured by the MSBuild integration test as the gzip bytes of the static web assets of a published app, ratchet-only like the npm ceilings: **core-only** and **full**. Today (before any move) both are the same
runtime tree (about 410 KB gzip of elements, js and CSS) plus the modules unit (69 KB) plus the gallery and skills assets the package serves (gallery 332 KB, skills about 436 KB gzip); the first Blazor phase records exact figures and sets the ceilings to them. Section 9 shows the goal: core-only falls by each moved extra's runtime JS and no extra's growth raises it.

## 8. Versioning, Pages and the release flow

- **Lockstep, one tag.** `core/VERSION` is the only source. `versioning.mjs set` stamps every artifact's generated manifest (`version`, `requires: plainkit <version>`, exact, not a range: the extras import core internals) and the `.csproj`; `check` fails when any manifest, `register.js` stamp or `.csproj` version differs. `check --release --tag vX.Y.Z` is unchanged (one tag).
- **Pages.** `build-pages.mjs` keeps copying the full `dist/` to `<pages>/dist/` (latest `main`, every existing URL unchanged) and additionally copies each assembled `dist-packages/<id>/` to `<pages>/packages/<id>/` with its `manifest.json` and `importmap.json`. Pages is still one deployment of the latest `main`, so the folders are "latest", never pinned. The site, gallery and per-element pages show each element's artifact id and its two load lines (Pages prefix, unzip). Disk cost is the extras twice (once in `dist/`, once in `packages/`), about 150 KB gzip, accepted for back-compat; Q18 asks whether `dist/` should later shrink to the overlay of core only.
- **Release assets.** Per tag, the GitHub release carries: `plainkit-<v>.zip` and one `<id>-<v>.zip` per extra, each with `<id>-manifest-<v>.json`; **FULL, first class**: `plainkit-dist-<v>.zip` (the all-in-one overlay, byte-identical in layout to today), `plainkit-modules-<v>.zip` and its manifest (same bytes as `plainkit.tools-<v>.zip`, one window), `dist-manifest.json`, `dist-manifest.extras.json`, `plainkit-skills-<v>.zip` (all skills, plus each extra's skill also inside its own zip) and the `PlainKit.Blazor` nupkg. `release.yml` loops over `packages.json`: `verify` runs the full verify including the per-artifact pack checks; `build` assembles and zips every artifact and packs the one nupkg into `release-assets`; `publish` creates the GitHub release and pushes the nupkg to NuGet with `--skip-duplicate`. A last step checks that every asset named by `packages.json` exists on the release and fails loudly listing the missing ones; the owner reruns the failed job. Nothing is pushed to npm: the step stays optional and unused (`NPM_TOKEN` absent), and is not extended to the new artifacts. Nothing publishes from `main`.
- **Partial failure** is a smaller risk than with registries (a GitHub release can be edited, only nuget.org cannot delete a version): the nupkg is the one irreversible artifact, pushed once, after the assets are verified. Exact requires pins mean a mixed set shows a version warning (section 5), never silent misbehaviour.
- **API surface per artifact.** `api-surface.mjs` stays one run over the whole repository (one baseline file) and records each item's artifact. A tag that moves between artifacts is not a surface change (no bump needed); a JS export that leaves a path core used to serve is, unless a shim keeps it (section 10). The baseline gains a `packages` map so the release PR shows moves. `versioning.mjs bump` reports the required level once for the set.
- **Changelog.** One `CHANGELOG.md`, one fragment directory; `scripts/changelog.mjs new` gains optional `--package <id>`, rendered as a prefix ("canvas: ...") so each artifact's README can link to its entries without a second compile step. The release PR template adds the artifacts table.
- `PUBLISHING.md` and `CONTRIBUTING.md` ("Versioning and releases") gain the artifact list, the Pages `packages/` layout and the zip-over-zip install, and no new registry setup.

## 9. Size ceilings and the way down

**What the existing ceilings mean now.** `core/tests/package-size.test.mjs` measures `npm pack --dry-run` of `core/` (883,476 packed / 3,271,119 unpacked bytes against 900,000 / 3,350,000). `npm pack --dry-run` needs no registry and no token; npm is not a distribution channel, but the tarball is the **measuring model** of "what a consumer takes in": its file list, its compressed size and its unpacked size. That role stays: the test keeps asserting the same top-level file list, relative `llms.txt` links and omitted files, and the numbers above remain the core's ceilings until a move lowers them. The consumer-facing equivalent is the zip, so `check-package.mjs` also asserts the zip of each artifact (below) and the size test reports the zip bytes next to the model; a zip ceiling is set from the first measurement in phase 1 (zip and tarball both deflate, so they track within a few percent) and ratchets down the same way. No ceiling is changed by this spec.

**Per-artifact ceilings from day one.** `packages.json` holds `maxPackedBytes` and `maxUnpackedBytes` (the model) and `maxZipBytes` per artifact; `package-size.test.mjs` becomes a loop over artifacts (same checks: closed top-level list per artifact, relative links in `llms.txt` resolve, omitted files stay omitted, plus a new check that the union of all artifacts covers `core/dist` minus the documented omissions and that no file ships in two). Each artifact's first ceiling is its measured size plus 1 percent and is lowered, never raised, like the core's; same rule as AGENTS.md "Size budgets are never raised". The rationale stays in the test's header, one line per change.

**`check-package.mjs` for zips.** Per artifact: the zip opens, holds only the files `packages.json` assigns (and the folder layout of `dist`), its `manifest.json` lists every file with a correct SRI hash and `requires` matches the version, `register.js` is present and stamped (extras), the metadata files list only that artifact's elements, the skill is present, and the zips of core plus all extras unioned equal the all-in-one dist zip (nothing lost, nothing twice). The nupkg checks stay as today plus those of section 6.

**Core ceilings go back down with each move**, set to the measured value of that phase's PR plus 0.5 percent. Estimates (to be measured and recorded on the issue per phase; method: assemble and measure before and after):

## 10. Backward compatibility and migration

- **Tags, props, events, CSS:** unchanged. Moving an element to an artifact does not change its API.
- **Existing Pages and zip users:** nothing breaks. Pages `dist/` and `plainkit-dist-<v>.zip` are the FULL shape, first class and permanent, the full overlay and keep every current path (`elements/dock.js`, `js/dock-model.js`), so a page that links them works unchanged and is the migration path "do nothing". The new artifacts are for consumers who want less: replace the dist zip with `plainkit-<v>.zip` plus the extras they use.
- **Old deep paths inside core's own zip/Pages folder** (`plainkit` without the extra): a page that imported `elements/dock.js` from a core-only unzip gets a 404 plus the missing-extra message of section 5. For a deprecation window (DECIDED: the break is released in 0.20 and the old paths are removed in 0.22; at least one minor, `deprecated: { since, remove, message }` as `versioning.mjs` already enforces) the **dist** zip and Pages `dist/` keep serving those paths; `plainkit` does not (it is new, so nobody depends on it). The dist zip's removal date is the migration table's schedule, Q8.
- **Dev-tool helper files** (row 1) are not documented API; they leave core without a shim and the changelog has a `breaking` entry (0.x: a minor release, `versioning.mjs bump` computes it). Module users already import `modules/*` from the modules zip or the Blazor package; `plainkit.tools` serves the same paths.
- **Blazor:** one package, so no assembly or namespace change and no new reference. The one new requirement is the declaration (`<PlainKitExtras>` or `AddPlainKit(o => o.Extras...)`): an app that uses `PkDock` without declaring `dock` gets the build warning PKB001, the startup/render diagnostic of section 6, never a blank component. There is no flip: with no declaration the default is FULL, permanently (owner clarification 2026-10-20), so existing apps keep working and need no declaration. An app that chooses core + modules and then uses `PkDock` without declaring `dock` gets PKB001 and the startup/render diagnostics. It ships with a `changed` changelog entry, the Blazor skill and README table; the sample declares `full` explicitly and a second configuration runs core + modules.
- **Skills and docs links** that named an element's reference file keep resolving through redirects (the Pages site) and stub files in `elements-layout.md` pointing to the extra for one window.

## 11. Testing and CI impact

- `scripts/verify.mjs` groups: `lint`, `node`, `dotnet`, `pack` stay; `pack` runs per artifact (the `CHECKS` table gains rows generated from `packages.json`, with FIX lines); `--changed` maps `core/{elements,components,pages,shells,modules}/<name>/` to its artifact (reads `meta.json` `package`) so a dock change runs the dock pack check and the element tests, not the whole set. - `needs-bootstrap`: `core/dist-packages` is generated by the bootstrap (after `build.mjs`), adding about 2 seconds; `generated.mjs check` covers it.

## 12. Risks

Dependency-graph surprises (core code reaching into a moved file; the import-graph and P1 tests find them before any move); duplicate module instances when an extra resolves a different core copy (identity browser case in all three forms, exact `requires`, the version warning in `registerExtra`, reusing the Blazor mismatch warning's wording); import-map mistakes in the side-by-side form (generated `importmap.json`, tested by pack-smoke); a partial release (the end check lists missing assets; the nupkg is pushed last and once); more moving parts for contributors (one `packages.json`, scripts read it, the PR flow is unchanged); metadata filtering bugs (an extra's CEM missing a tag: a test compares the union of all CEMs to the old single file until it is retired); documentation sprawl (one Packages page, README tables generated from `packages.json`); the extras served twice on Pages (accepted, Q18); users who want one download (`plainkit-dist` stays); an extra that other extras start depending on (P1 limits requirements to the declared ones; `svg` -> `canvas`, `dock` -> core); the Blazor hand-written files that mix tool and core concerns (phase 1 measures it first). Dropped by the owner correction: scope ownership and npm publish ordering.
