# Packaging (sub-packages or not) and how we benchmark and stay fast

Status: research and proposal for the owner. No production code is changed by this document. Related: #979 (same-page size comparison), #514 (app entry graph), `scripts/bench/README.md` (the existing benches), `core/tests/budgets.test.mjs`, `core/tests/app-budgets.test.mjs`.

Measured on `origin/integration-0.13` (d5a8b343, version 0.12.0), after `npm ci` and `node scripts/bootstrap.mjs`, on Windows 11, with headless Chrome through `scripts/bench/load.mjs --runs 3`, the repo's own esbuild for bundles, and Node zlib for gzip (level 9) and brotli (default quality). Numbers marked *unverified* were not fetched or reproduced here.

## 1. Question

Should the dist be split into sub-packages so a small app pays only for what it uses, to compete with small frameworks (Lit, Preact, Svelte, Alpine, htmx, Shoelace/Web Awesome, vanilla web components), and how do we measure speed and keep it?

Short answer: **no sub-packages now.** The cost model is already per element. What hurts a small app is (a) request count and the per-file compression penalty, (b) a package that ships 8.7 MB of which a browser loads a few hundred KB, and (c) one defect that defeats bundlers (3.4). All three are fixable without splitting the package. Build the benchmark and the ratchet first (section 6); let the numbers decide whether a lite target (option C) is ever needed.

## 2. How it is built and shipped today

- One npm package `plainkit` (`core/package.json`: `files: ["dist", "!dist/modules", ...]`, `sideEffects: false`, **no `exports` or `main` field**). One NuGet package `PlainKit.Blazor` carrying a copy of `dist` as static web assets. The Pages site serves the same `dist`. A release is a tag equal to `core/VERSION` (`PUBLISHING.md`).
- `core/dist` is generated by `core/tools/build.mjs`: one ES module per element (`dist/elements/<name>.js`: template, CSS and behaviour, esbuild-minified, not bundled, importing shared helpers from `dist/js/*.js`), `elements/registry.js` (tag to module; 5.0 KB raw, 1.1 KB gz), one `plainkit.min.css` for the light DOM, and `plainkit.js` re-exporting `js/plainkit.js` (init, invokers, loader, theme, colour, page).
- A page loads `plainkit.js`; `loadElements` scans for undefined `pk-*` tags, fetches the registry once and dynamically imports only the modules those tags need (`js/loader.js`; a MutationObserver handles later additions). Lazy per-element loading therefore already exists and is the default path.
- `dist` is 9.7 MB on disk. The npm tarball is 2.1 MB packed, 8.7 MB unpacked, 524 files. Runtime: `elements/` 1.5 MB (0.6 MB of it `api.json`, metadata), `js/` 0.55 MB, CSS 32 KB. Not loaded by a browser: `gallery/` 1.4 MB, `skills/` 1.4 MB, `llms-full.txt` 1.2 MB, `custom-elements.json` 1.0 MB, `web-types.json` 0.4 MB, `tools/` 0.3 MB.
- Budgets (`core/site/scorecard/scoring.data.js`): page CSS 10 KB gz (target 8), element 4 KB gz, base runtime 2.8 KB, JS module 6 KB, base script set 10 KB, `appEntryGzKb` hard cap 22 KB (#514), page type 3 KB. All are size-only, per file (the entry graph as one concatenated gzip), gzip-only. None measures a whole served page, requests, brotli or time. The wall-clock benches in `scripts/bench/` are deliberately outside CI.

## 3. Findings (measured)

### 3.1 What a page costs today (unbundled dist, as served)

"JS gz" is the sum of each file gzipped on its own, which is what a server that compresses per file sends. CSS is `plainkit.min.css` (26.7 KB raw, 6.9 KB gz, 5.9 KB br). "Shared core" is `plainkit.js`, its static graph and the registry: 13 files, 20.9 KB raw, 8.8 KB gz, 7.8 KB br.

| Page | JS files (+1 css, +1 html) | JS raw | JS gz | JS br | JS+CSS gz | JS+CSS br |
|---|---|---|---|---|---|---|
| Core only (no element) | 14 | 20.9 KB | 8.8 KB | 7.8 KB | 15.7 KB | 13.7 KB |
| One `pk-button` | 20 | 38.1 KB | 15.6 KB | 13.7 KB | 22.5 KB | 19.6 KB |
| Form (field, input, select, checkbox, textarea, button) | 25 | 68.8 KB | 26.8 KB | 23.5 KB | 33.7 KB | 29.4 KB |
| Data table (table, pager, toolbar, input, button) | 27 | 69.0 KB | 27.1 KB | 23.9 KB | 34.0 KB | 29.8 KB |
| `mountApp` entry graph (`js/app.js`, no page type or module) | 20 | 49.9 KB | 24.2 KB | 21.7 KB | 31.1 KB | not measured |

Browser measurement (`scripts/bench/load.mjs`, median of 3, first run discarded; elements are the first N of a fixed list; the request count includes the HTML and the CSS):

| Elements on the page | Requests | JS files | Chain depth | Raw | Sent gz (Slow 4G, 4x CPU) | FCP unthrottled / throttled | All upgraded unthrottled / throttled |
|---|---|---|---|---|---|---|---|
| 0 | 10 | 8 | 3 | 45.2 KB | 14.4 KB | 40 / 504 ms | 66 / 744 ms |
| 1 | 14 | 12 | 4 | 56.6 KB | 18.6 KB | 44 / 528 ms | 96 / 1,177 ms |
| 10 | 23 | 21 | 4 | 91.1 KB | 31.6 KB | 44 / 516 ms | 124 / 1,299 ms |
| 30 | 47 | 45 | 4 | 166.2 KB | 62.3 KB | 44 / 520 ms | 236 / 1,911 ms |

The bench's wire figure and my per-file gzip sum differ by a few KB (different compressor and eager-file set); both are the same order of magnitude. Section 6 defines one method so they stop disagreeing.

### 3.2 Shared core versus per element

- 129 element modules, 220.8 KB gz in total, median 1.5 KB, largest 4.1 KB.
- A one-button page is 15.6 KB gz of JS, but the button is about 3 KB of it. The rest is the shared graph (`element.js` 1.8 KB, `log.js` 1.8 KB, `loader.js` 0.9 KB, `icon-sprite`, `breakpoints`, `safe-url`, the registry): about 56 percent of the one-button page and about 33 percent of the form page. The marginal element is cheap: the six form elements add 11 KB gz over the one-button page, because the shared files are already loaded.
- Everything reachable from all elements: 180 files, 658 KB raw, 260 KB gz as separate gzips.

### 3.3 The real overhead: many small files compress badly

The same graphs bundled into one minified ES module with esbuild (with `ignoreAnnotations`, see 3.4):

| Graph | Unbundled, gz sum | One bundle, gz | One bundle, br | gz saving |
|---|---|---|---|---|
| core + `pk-button` | 15.6 KB (20 files) | 8.7 KB | 7.8 KB | 45 percent |
| core + form elements | 26.8 KB (25 files) | 15.1 KB | 13.5 KB | 44 percent |
| core + table elements | 27.1 KB (27 files) | 20.8 KB | 18.7 KB | 23 percent |
| `mountApp` entry graph | 24.2 KB (20 files) | 13.4 KB | 11.9 KB | 45 percent |
| All 129 elements + core | 260 KB (180 files) | 163.6 KB | 122.1 KB | 37 percent |

Small modules cannot share a compression dictionary, repeat boilerplate, and each costs a request and a module-graph round trip (chain depth 4). A bundle of exactly what a page uses is 23 to 45 percent smaller in gzip and one request instead of 20 to 27. The 22 KB `appEntryGzKb` cap is measured as one concatenated gzip with comments stripped; the entry graph as served is 24.2 KB gz, so that budget understates the wire by about 10 percent.

### 3.4 A defect that matters more than splitting: `"sideEffects": false`

`core/package.json` declares `"sideEffects": false`, but every element module registers itself by calling `define(...)` at import. esbuild (and webpack and Rollup, which honour the field) drop `import "plainkit/.../button.js"` as dead code: my first bundle run produced a 0-byte output with "Ignoring this import because ... was marked as having no side effects". A bundler user who imports an element for its registration gets no element. There is also no `exports` map, so deep imports work only by filesystem path and there is no stable public entry. This is a bug independent of the packaging decision and is Option A's first step. I did not file an issue (read-only task); the owner should.

### 3.5 Does the per-element lazy loader already deliver the benefit of sub-packages?

For a page served from a CDN or the Pages-style `dist` prefix: **yes, most of it.** The loader imports only modules for tags that exist, each cacheable on its own; unused elements cost zero bytes and zero parse time. Cost scales roughly linearly with distinct elements (about 1.5 requests, 2 KB gz and 5 ms of upgrade per extra element unthrottled, from the rows above). Sub-packages change what sits in `node_modules`, not what the browser downloads.

What lazy loading does not deliver: fewer requests (it adds the registry and one file per element), a better compression ratio (3.3), a shorter dependency chain (4 deep, each a round trip on a real network), or a smaller install and CI cache (8.7 MB unpacked, mostly docs and metadata). The first three are fixed by a per-page bundle, the last by an `exports` map and a leaner tarball.

For Blazor the question barely applies: the NuGet package ships all of `dist` as static web assets and the app loads the same lazy loader, and the framework itself (SignalR, `blazor.web.js`) dwarfs any element saving. Splitting would multiply NuGet packages (versions cannot be deleted, only unlisted) for no browser gain.

### 3.6 Comparison with small frameworks (not apples to apples)

Published library sizes from the public Bundlephobia API, fetched 2026-10-11 (minified, gzip): Lit 3.3.3 about 6.0 KB; Preact 11.0.1 about 5.0 KB; Svelte 5.57.2 about 10.8 KB (the whole runtime import; a compiled Svelte app ships only what it uses, so this overstates real cost); Alpine 3.17.4 about 19.1 KB; htmx 2.0.11 about 18.2 KB. Shoelace and Web Awesome requests were rate-limited (HTTP 429): *unverified*, no figure quoted. A React or Vue component-library baseline was not fetched: *unverified*.

How to read them: Lit and Preact are bases with no components. Plainkit's equivalent base (loader, element base, logging, init) is 8.8 KB gz unbundled, and core plus one button is 8.7 KB gz JS bundled, plus 6.9 KB CSS. The defensible claim is "the base is in Lit and Preact's range, and 129 styled, accessible components sit on top". It is not "smaller than Lit". A real comparison needs the same page built in each tool, which is #979; do not publish the table above as a competitor comparison until then.

## 4. Options

### A. Keep one package; add an `exports` map, correct `sideEffects`, and a per-page bundle (recommended)

- `core/package.json`: `exports` with `.` (init and loader), `./elements/*`, `./css`, `./app`, `./skills/*`, and the audit bin kept separate; `sideEffects` becomes an array naming the element files and CSS. Keep `./dist/*` mapped for one release.
- Ship an optional bundle step: a small script (esbuild is already used by `build.mjs`) or a documented esbuild/Vite recipe that emits one minified module for a project's element list (3.3).
- Trim the tarball: drop `gallery`, `tools`, `llms-full.txt` from the runtime package (they stay on Pages and in the skills zip; `custom-elements.json` and `web-types.json` give editors support and may stay). Estimated 8.7 MB unpacked down to about 3 to 4 MB (from the du figures; not packed and measured).
- Cost: low. One package, one version, NuGet unchanged, one docs page on bundling. The `api-surface` baseline can cover the exports list.
- Risk: an `exports` map breaks anyone deep-importing undeclared paths; the compatibility mapping above limits it.

### B. Scoped sub-packages: `@plainkit/core`, `@plainkit/elements-*`, `@plainkit/app`, `@plainkit/blazor`

- Measured browser benefit: none (3.5). Possible benefit: a smaller `node_modules` and clearer ownership.
- Cost: high. Elements import shared `js/` helpers and components import elements, so a tier split is natural but a per-element split is a 129-package dependency matrix, each with an exact-pinned peer on core and one release train. `release.yml` goes from one publish to N, and a partial failure leaves a mixed state on npm. `versioning.mjs` checks a single `VERSION`; `generated.mjs`, the skills builder, `check-package.mjs`, the api-surface baseline and the Pages build all assume one `dist`. NuGet must carry `dist` as static web assets, so it either gains N packages or keeps its own copy and duplicates the problem. Every doc snippet and agent skill saying `import 'plainkit'` changes. Estimated weeks of work plus permanent release overhead.
- Reconsider only with evidence: a coarse three-way split (core + elements, app framework, tooling) if the benchmark shows installs or the app layer are what hurts.

### C. A lite build target (a profile of the same package)

- Drop what a small page rarely needs: logging (`log.js` is 1.8 KB gz and in every graph), MutationObserver observation, the registry fetch (replace with a build-time tag list: one request and one round trip fewer), theme and colour machinery for pages that do not theme. A projection, not a measurement, is about 6 KB gz for the one-button page against 8.7 KB today; it needs a prototype.
- Cost: medium. Two entry points to keep equivalent, a drift gate, and constraints from "no new base-class hooks". Implement as build-time flags in `build.mjs` (debug logging stripped behind a define), not a forked source tree.
- Do this only if the benchmark shows the base cost is the competitive gap, after A.

## 5. Recommendation

1. Do **A** now: fix `sideEffects`, add `exports`, trim the tarball, document and ship the per-page bundle. It captures a 23 to 45 percent wire saving and one request instead of 20 to 27, which exceeds anything sub-packages offer, at a fraction of the cost.
2. Build the benchmark and the regression ratchet (section 6) before further size work; the existing budgets measure per file, gzip only, with no requests and no time.
3. Reassess **C** with the harness numbers. Decline **B** unless installs or the app layer prove to be the problem; it carries a permanent release cost and no measured browser benefit.

## 6. Benchmark plan

### What to measure

| Measure | Why | Gate? |
|---|---|---|
| Bytes over the wire, gzip and brotli, cold, for HTML + JS + CSS of each reference page | the competitive number (#979) | yes (deterministic) |
| Request count and chain depth | latency on a real network | yes |
| Static graph size (raw, gz, br) of served files and of the bundle-for-page | catches growth in shared core | yes |
| FCP, LCP, CLS, INP (synthetic click, type, sort) | user-facing | trend only |
| JS execute time: evaluation + upgrade, main-thread time and long tasks, at 1x and 4x CPU | parse and run cost | trend only |
| Heap after load and after N instances; listeners and DOM nodes | memory and leaks | counts yes, bytes trend |
| Per-element render cost (create, first render, update, 2,000 instances) | element-level regressions | counts (renders per change) yes, time trend |
| Cold versus warm: empty cache, then HTTP-cached reload | what a returning user pays; tests the cache value of per-file modules | bytes yes, time trend |

### Harness

- Extend `scripts/bench/` (it already has the headless-Chrome DevTools driver, a compressing static server, medians, throttling profiles and the `load`, `runtime`, `scale`, `pages`, `package`, `blazor` scripts). Add `scripts/bench/wire.mjs`: serve each reference page from memory with gzip and brotli, load it cold and warm, write one JSON (page, tool, variant, bytes gz/br, requests, depth, per-run timings as median/min/max, versions).
- Reference pages in `scripts/bench/pages/` (committed, tiny): one button; a form with validation; a data table with sort and paging; a dialog; a `mountApp` shell with two modules. Variants: Plainkit as served (lazy per element), Plainkit per-page bundle (option A), Plainkit lite (if built).
- Competitor builds (Lit, Preact, Svelte, Vue, React, Shoelace or Web Awesome, htmx/Alpine for the non-component tools) are the #979 deliverable: the same pages, each built with its normal production tooling from a pinned `package.json` and lockfile under `scripts/bench/compare/`, with its own install outside the main `npm ci`. Record exact versions and build configs beside the results so the table repeats.

### CI trend and regression gate

- A workflow `bench.yml` runs nightly on `main` and on `release/*` pull requests: the deterministic part (bytes, requests, depth, graph sizes) plus the timing part on one runner class. It stores `bench-results.json` as an artifact and appends it to a history file on an orphan `bench-history` branch (the same idea as the `issue-images` branch and the ui-review cache), so a docs trend page can plot it. Timings are reported with min and max and never fail a build.
- **New ratchet**: `core/tests/page-weight.test.mjs` computes from `core/dist`, with no browser, the served gzip and brotli bytes and request count of each reference page (the graph walk used for this document is about 20 lines) and compares them to `core/site/scorecard/page-weight.baseline.json`. It fails when any page grows more than a small tolerance (start at 2 percent or 200 bytes); the baseline can only be lowered in a pull request, like the other budgets. A change that adds a shared import to `element.js` then shows on every page row at once, which the per-file budgets cannot see.
- Timing gate: none on pull requests (noise, as `scripts/bench/README.md` says). The nightly compares the median to the trailing 7-night median and files or updates one issue (the mechanism of the browser nightly, #752) when a page's execute time or LCP regresses by more than 20 percent twice in a row.
- Keep the existing count guards (one `import` and one `init` per 200 Blazor components, one render per storm).

### Cadence

Per pull request: `page-weight.test.mjs` (seconds, in the node job). Nightly on `main`: full wire and timing. Release: the full benchmark and a refreshed competitor table attached to the release notes. Quarterly: re-pin competitor versions.

## 7. Open questions for the owner

1. **Which claim do we want?** "Base in Lit's range, plus a component set" (honest today) or "beats Lit on a comparable page" (needs option C). Recommendation: the first; revisit after #979.
2. **Fix `sideEffects: false` and add an `exports` map now, as a 0.13 change?** It silently breaks bundler users today. Recommendation: yes, keep `./dist/*` mapped for one release, with a breaking changelog fragment.
3. **Ship a per-page bundle step in the package?** Recommendation: yes, a small script plus a Vite/esbuild recipe in the docs, with esbuild an optional peer.
4. **Trim the npm tarball** (gallery, tools, `llms-full.txt)`? Recommendation: yes; keep `custom-elements.json` and `web-types.json` for editors, serve the rest from Pages and the skills zip.
5. **Appetite for the coarse three-way sub-package split later?** Recommendation: no until the benchmark shows installs or the app layer hurts; revisit at 1.0.
6. **Prototype a lite target (build-time flags: no logging, no registry fetch)?** Recommendation: yes after the benchmark exists, and keep it only if it saves at least 2 KB gz on the one-button page.
7. **Where does the competitor build live and who pays for its CI?** Recommendation: `scripts/bench/compare/` with its own lockfile, run by `bench.yml` only, results on the `bench-history` branch, nothing added to `main`'s install.
8. **Re-express the budgets as served bytes?** Today they are per-file gzip and the entry graph is one concatenated gzip (about 10 percent under the served figure). Recommendation: keep them, add the page-weight ratchet beside them, show both in the scorecard, raise nothing.

## 8. Caveats

- One machine, headless Chrome, three runs: timings are indicative. The graph-walk and bench wire figures differ slightly; the new harness must pick one method.
- Bundle numbers use `ignoreAnnotations` to bypass the `sideEffects` flag and include every shared helper the elements import; a real app might tree-shake a little more.
- The lite figure (about 6 KB) is a projection.
- Competitor figures are Bundlephobia library sizes, not the same page; Shoelace and Web Awesome are unverified.
