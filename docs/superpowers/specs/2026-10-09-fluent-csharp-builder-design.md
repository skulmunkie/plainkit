# A fluent C# builder API for PlainKit.Blazor, generated from the mappings

Status: design for the owner to confirm before anything is built. No production code is written by this document or its pull request.

Owner request: build UI from C# (loops, data-driven pages, libraries, tests) with a fluent API, next to the Razor components, for example `Pk.Button().Primary().IconName(PkIcons.Save).OnClick(Save)`, with nested composition (cards, stacks, forms, tables). Standing rules that bound the design: core holds the functionality, Blazor is a thin 1:1 **generated** wrapper, `blazor/handwritten.json` and its baseline only shrink (every hand-written line is debt), the builder costs nothing when unused (trimming friendly, no reflection of our own), and lean code.

## 1. Goals, non-goals, and why it is separate from the Razor API

### Goals

1. Every generated component (117 today, from `blazor/mappings/*.json` and `core/dist/elements/api.json`) has a builder with the same parameters, slots and events, **generated by the same run** of `scripts/generate-blazor.mjs`. No per-element hand-written builder code.
2. The builder renders **the Razor component itself** (`OpenComponent<PkButton>` plus its parameters). There is no second implementation of attribute rendering, `class` merging, event wiring, `PkCallbackSlot` or `EditContext` handling: markup is identical by construction, and a parity test proves it.
3. Compile-time checking for both APIs: enum values, and a typed icon list (`PkIcons.Save`) usable as a plain string in Razor too.
4. Zero cost when unused: builders are plain classes, referenced only by code that uses them; the trimmer removes the rest. No `Activator`, no `MakeGenericType`, no reflection scanning of our own.
5. Works in Razor (`@node`), in a plain C# `ComponentBase` (`BuildRenderTree`), in a bUnit test, and in a library that returns `RenderFragment`s.

### Non-goals

- Not a replacement for Razor markup: Razor stays the documented default for pages written by hand.
- No new elements, no new behaviour, no layout recipes: a builder cannot do anything a component cannot.
- No hot-reload / design-time story beyond what C# gives.
- No builder for Microsoft's components (`EditForm`, `InputText`); one generic escape hatch covers them (section 3.6).
- No change to core, the mappings' meaning, the tiers or the namespaces.

### Comparison

| | Razor components (today) | Fluent C# builder (this spec) | Microsoft Fluent UI Blazor (`Microsoft.FluentUI.AspNetCore.Components`) |
| --- | --- | --- | --- |
| Authoring | Markup, `@bind-Value` | C# method chains, loops and `if` are ordinary C# | Razor components only; parameters are typed, there is no C# builder |
| Typed parameters | Yes (enums, `EventCallback<T>`, `RenderFragment`) | Same types, same names | Yes |
| Services | `AddPlainKit()`, `IPkNotifications`, `PkRuntime` | Same services; builders need none of their own | `AddFluentUIComponents()` plus services for dialog, toast, message bar, tooltips and design tokens (`IDialogService`, `IToastService`), imperative C# calls that open a component by type |
| Data-driven UI | `@foreach` | `Select(...)`, `Add(items.Select(...))` | `@foreach`, or the dialog service for a component type + data model |
| Testing | bUnit `Render<T>` | bUnit `Render(node)` or `node.Render()` | bUnit `Render<T>` |
| Output | Web components (`pk-*`), no framework CSS at runtime | The same components | Fluent web components, Microsoft design system |

Why a builder is a separate surface and not a feature of the components: a Razor component cannot be constructed with `new` and configured by a chain (`new PkButton().Primary()` would create a component instance that no renderer owns, and it throws when rendered); a chain needs a different, light, renderer-agnostic object. Fluent UI's services are imperative **host** services (open this dialog), not a UI composition API; they are complementary and the builder does not replace `IPkNotifications` or a dialog host. The builder is therefore a *description of a component tree* that is turned into a `RenderFragment`.

## 2. API shape

### 2.1 The entry point and the nodes

One static class `Pk` (generated, partial) holds one factory per component, named by the tag without `pk-` and in Pascal case: `Pk.Button()`, `Pk.Card()`, `Pk.Stack()`, `Pk.DataTable<TItem>()`. The same name as the component minus `Pk` keeps it guessable (`PkAppShell` becomes `Pk.AppShell()`). `Pk.Text("...")` makes a text node, `Pk.Of<TComponent>()` is the generic escape hatch (3.6).

Everything chainable derives from one small hand-written generic base (the only hand-written part, section 3.1):

```csharp
public abstract class PkBuilder<TSelf, TComponent> : IPkNode where TComponent : IComponent
{
    public TSelf Set(string parameter, object? value);                 // untyped; generated methods call it
    public TSelf Attr(string name, object value);                      // goes into AdditionalAttributes (id, data-*, aria-*)
    public TSelf Class(string classes);                                // merged with the component's own classes (PkElementBase.Css)
    public TSelf Key(object key);                                      // @key
    public TSelf Add(params IPkNode[] children);                       // the default slot (ChildContent)
    public TSelf Add(IEnumerable<IPkNode> children);                   // a loop result
    public TSelf Add(string text);                                     // a text node
    public TSelf When(bool condition, Func<TSelf, TSelf> apply);       // conditional parts without breaking the chain
    public RenderFragment Render(IHandleEvent? receiver = null);       // the bridge to Razor (2.3)
    public static implicit operator RenderFragment(PkBuilder<TSelf, TComponent> b) => b.Render();
}
```

`IPkNode` is `{ void Render(RenderTreeBuilder b, ref int seq, IHandleEvent? receiver); }`. Strings, `RenderFragment`s and builders are nodes (`implicit operator IPkNode` from `string` and `RenderFragment`). The generated parameters are typed; `Set` is the one internal funnel.

### 2.2 Worked examples

All examples are real API names as the generator would produce them from the current mappings (`PkButton`: `Variant`, `Size`, `Disabled`, `Busy`, `Icon` (bool, icon-only), `IconName`, `OnClick`, slots `ChildContent`, `StartContent`, `EndContent`; `PkCard`: `Heading`, `ActionsContent`, `FooterContent`). A `using static PlainKit.Blazor.Pk;` makes the factories bare (`Button()`).

**Owner UI rule (icons by form factor).** The rule is: small form factor icons instead of text, medium icons where space is limited, large icon plus text. Verified in the repo: `pk-button` has no option that collapses its label by width (no such prop in `button.meta.json`, no such CSS), and `core/base/utilities.css` has only `u-sr-only` (visually hidden), no responsive hide utility. The examples therefore always give the icon an accessible name and keep the text as a real child; **making the label collapse by container width is a core change (open question Q8) and is not done in the builder**. Until then examples use `Icon + text`, with the text hidden from sight but still read by assistive technology where the owner wants icon-only (`u-sr-only`).

**Example 1: a button with an icon**

```csharp
var save = Pk.Button().Primary().IconName(PkIcons.Save).Add("Save").OnClick(SaveAsync);
// icon only, named for assistive technology (small screens)
var saveSmall = Pk.Button().Primary().IconOnly().IconName(PkIcons.Save).AriaLabel("Save").OnClick(SaveAsync);
// larger screens: icon plus text, the icon in the start slot
var saveLarge = Pk.Button().Primary().Start(Pk.Icon().Name(PkIcons.Save)).Add("Save");
```

`Primary()` is the shortcut for `Variant(ButtonVariant.Primary)` (3.3). `IconOnly()` is the bool `Icon` parameter under a builder alias (section 3.3, naming: a `Icon()` method would collide with the icon *name* in every reader's mind).

**Example 2: a card with header actions and a menu**

```csharp
Pk.Card().Heading("Order 1042").Level(2)
    .Actions(
        Pk.Button().Ghost().IconOnly().IconName(PkIcons.Edit).AriaLabel("Edit").OnClick(Edit),
        Pk.CardMenu().Add(
            Pk.MenuItem().Add("Duplicate").OnClick(Duplicate),
            Pk.MenuItem().Add("Delete").OnClick(DeleteAsync)))
    .Add(Pk.Text("Placed 3 March, 2 items."))
    .Footer(Pk.Button().Add("Close").OnClick(Close));
```

Slots: `ActionsContent` becomes `Actions(...)` and `FooterContent` becomes `Footer(...)` (rule in 3.4); the default slot is `Add(...)`.

**Example 3: a form with fields, validation and a submit**

```csharp
var form = Pk.Of<EditForm>().Set(nameof(EditForm.Model), _order).Set(nameof(EditForm.OnValidSubmit), Cb(SubmitAsync))
    .Content(ctx => Pk.Stack().Add(
        Pk.Field().Label("Customer").Add(
            Pk.Input().Bind(() => _order.Customer, v => _order.Customer = v)),
        Pk.Field().Label("Quantity").Add(
            Pk.Input().Type("number").Bind(() => _order.Quantity, v => _order.Quantity = v)),
        Pk.Of<ValidationSummary>(),
        Pk.FormActions().Add(Pk.Button().Primary().Type("submit").IconName(PkIcons.Save).Add("Save"))));
```

`EditForm` is Microsoft's component, so it goes through `Pk.Of<TComponent>()` with the untyped `Set`; **PlainKit's own controls** are fully typed. The cascading `EditContext` reaches `Pk.Input()` because the controls are rendered inside `EditForm`'s `ChildContent` (a normal component tree); `PkFormControlBase` therefore marks the field modified and shows the validation state exactly as in Razor. See 2.5 for `Bind`.

**Example 4: a data table with typed columns and Load**

```csharp
Pk.DataTable<Order>()
    .Columns(new PkTableColumn<Order> { Key = "id", Label = "No." }, new PkTableColumn<Order> { Key = "customer", Label = "Customer", Sortable = true })
    .Load(async req => new PkListResult<Order>(await _api.PageAsync(req), await _api.CountAsync(req)))
    .RowId(o => o.Id.ToString())
    .Selectable().OnRowClick(Open);
```

`PkDataTable<TItem>` is a hand-written generic component (category `typed-generics`). The generator reads its `[Parameter]` declarations to emit the builder (3.5); the column type is whatever the component already declares (verify the exact record shape at implementation; the sketch uses the type as it exists in `PkTableColumn.cs` today).

**Example 5: a page built in a loop from data**

```csharp
protected override void BuildRenderTree(RenderTreeBuilder b) =>
    Pk.Stack().Add(
        _sections.Select(s =>
            Pk.Card().Heading(s.Title).Key(s.Id).Add(
                s.Items.Select(i => Pk.Cluster().Add(
                    Pk.Text(i.Name),
                    Pk.Badge().Add(i.Status)))))
    ).Render(this)(b);
```

A `Select` over a list returns `IEnumerable<IPkBuilder...>`, accepted by `Add(IEnumerable<IPkNode>)`. `.Key(...)` becomes `@key`.

**Example 6: slots and named slots**

```csharp
Pk.AppShell().Brand(Pk.Text("Acme")).Nav(Pk.SideNav() /* hand-written component: see 3.5 */)
    .Header(Pk.Toolbar().Add(Pk.Button().Ghost().IconOnly().IconName(PkIcons.Menu).AriaLabel("Menu")))
    .Add(content);
```

A named slot is a method named after the slot (mapping `slot: "start"` gives `Start(...)`), and the same name rules as the parameter (3.4). A slot takes nodes (`params IPkNode[]`) or a `RenderFragment`; a text-typed slot (`string` in the mapping) takes `Header("text")`.

**Example 7: events and async callbacks**

```csharp
Pk.Button().Primary().Add("Reload").OnClick(async () => await LoadAsync());          // Func<Task>
Pk.Select().Bind(() => _kind, v => _kind = v).OnChange(e => Log(e.Value));          // Action<PkChangeEventArgs>
Pk.Dialog().Open(_open).OnClose(() => { _open = false; });                           // Action
```

Every event parameter `EventCallback`, `EventCallback<T>` gets overloads `Action`, `Action<T>`, `Func<Task>`, `Func<T, Task>` and `EventCallback`/`EventCallback<T>` itself. The builder creates the callback with `EventCallback.Factory.Create(receiver, ...)`: the **receiver** is the component whose state the handler changes, so Blazor re-renders it after the handler (what Razor does implicitly with `this`). The receiver is supplied at the root: `node.Render(this)` (see 2.3); a node rendered with `Render()` and no receiver still calls the delegate but triggers no re-render of the host.

**Example 8: toasts and dialogs**

Toasts stay on the service: `await Notifications.SuccessAsync("Saved")` (`IPkNotifications`, unchanged). `pk-toast` and `pk-dialog` as markup are builders like any other: `Pk.Dialog().Heading("Delete order?").Open(_confirm).Add(...).Footer(...)`. No imperative "open a dialog of type X" service is added (that is the Fluent UI model and would be new hand-written Blazor code; see Q7).

### 2.3 Turning a builder into something renderable

| Where | How |
| --- | --- |
| In Razor | `@node.Render(this)`; `@node` alone also works when the node is typed as `RenderFragment` (`RenderFragment f = node;` uses the implicit conversion) |
| A plain C# component | `protected override void BuildRenderTree(RenderTreeBuilder b) => node.Render(this)(b);` |
| A library | return `RenderFragment` (`=> node.Render()`) or `IPkNode` |
| Passing into a component that takes `RenderFragment` | `<PkCard ChildContent="@node.Render(this)" />` or the implicit conversion |
| bUnit | `ctx.Render(node.Render())` (`BunitContext.Render(RenderFragment)`), or a tiny `Render<TComponent>` as today. The builders need no test-only API |

Implementation: `Render` creates a `RenderFragment` that calls `b.OpenComponent<TComponent>(seq)`, `b.AddComponentParameter(seq, name, value)` per stored parameter, `b.AddAttribute(seq, "ChildContent", (RenderFragment)(...))` for the slots, then `CloseComponent`. `OpenComponent<TComponent>` is annotated for the trimmer (`DynamicallyAccessedMembers(Properties)` on the component type argument) the same way `DynamicComponent` and the Razor compiler's output are, so the component's parameters stay and nothing else is kept alive.

### 2.4 Typed icons and enums

`PkIcons.Save` and the enum shortcuts: section 4. Both are plain values the builder and the Razor components accept.

### 2.5 Two-way binding for form controls with EditContext

Razor writes `@bind-Value="m.Name"`, which the compiler expands to `Value`, `ValueChanged` and `ValueExpression`. The builder's generated form-control methods (the mappings with `model.field`) are:

```csharp
public PkInputBuilder Bind(Expression<Func<string?>> field, Action<string?> set);      // reads the value and names the field
public PkInputBuilder Bind(string? value, Action<string?> set, Expression<Func<string?>> field); // no compile, for AOT hot paths
```

The first reads the value by compiling the expression once and takes `ValueExpression` from it (what `InputBase` does for the field name; the compile is cached per expression instance). The second takes the three things Razor generates, with no expression compile. Both set `Value`, `ValueChanged` (an `EventCallback` over `set`) and `ValueExpression`; the existing `PkFormControlBase` then does everything else (modified tracking, `invalid`). A `Values`/`ValuesChanged` pair (the multi-select forms) gets the same two overloads. Which of the two is the default is Q4.

## 3. How it is generated

### 3.1 The hand-written part (honest accounting)

A generated builder needs a runtime to stand on. Everything below is **new hand-written Blazor code**, proposed as a new category `builder-runtime` in `blazor/handwritten.json` with line budgets, and it is the only hand-written part:

| File | Contents | Lines (estimate) |
| --- | --- | --- |
| `Builders/PkBuilder.cs` | `PkBuilder<TSelf, TComponent>`, `IPkNode`, text node, `Render`, `Set`/`Attr`/`Class`/`Key`/`Add`/`When`, event-callback factories | 90 to 120 |
| `Builders/PkOf.cs` | `Pk.Of<TComponent>()`, the generic escape hatch, as a builder with no named methods | 15 |

About 130 hand-written lines against about 117 builders of generated code. The team can decide that this is acceptable debt-free runtime (it fits the existing "base" category: `PkElementBase`, `PkFormControlBase`), but it **is** hand-written Blazor and needs the baseline entry; nothing else in this design is. If the owner would rather have none at all, the base can be generated too, as one `PkBuilderBase.g.cs` template emitted by the generator (the generator then carries the 120 lines instead of the repo; the logic is the same and the generator is Node code that is already allowed to be large). Recommendation: generate it (Q2).

### 3.2 What the generator emits per element

`modelElement(el, mapping, reg)` already returns everything: `params` (name, C# type, doc), `children` (slots), `handlers`/event parameters, `field`, `typeparam`. A new `renderBuilder(model, ns)` consumes that **same model** (so the component and its builder cannot drift) and writes one file per element, `Generated/Builders/PkButtonBuilder.g.cs`, plus `Pk.g.cs` (the factories) and `PkIcons.g.cs`:

```csharp
// Generated by scripts/generate-blazor.mjs. Do not edit.
namespace PlainKit.Blazor;
public sealed class PkButtonBuilder : PkBuilder<PkButtonBuilder, PkButton>
{
    public PkButtonBuilder Variant(ButtonVariant v) => Set(nameof(PkButton.Variant), v);
    public PkButtonBuilder Primary() => Variant(ButtonVariant.Primary);
    public PkButtonBuilder Disabled(bool v = true) => Set(nameof(PkButton.Disabled), v);
    public PkButtonBuilder OnClick(Action<MouseEventArgs> h) => Set(nameof(PkButton.OnClick), Cb(h));
    public PkButtonBuilder OnClick(Func<MouseEventArgs, Task> h) => Set(nameof(PkButton.OnClick), Cb(h));
    public PkButtonBuilder Start(params IPkNode[] n) => Set(nameof(PkButton.StartContent), Fragment(n));
    ...
}
```

A class per element (not extension methods on a generic base) because the chain must return the concrete type without generic gymnastics at the call site, and because a class per element is trimmed when unused. `nameof(PkButton.Variant)` ties the string to the component at compile time: a renamed parameter fails the build, never at run time. Extension methods on a shared generic fluent base were rejected: every method would carry a `this TBuilder` generic parameter and IntelliSense would offer every method for every builder.

The generator reuses `modelElement`, so skipped parameters (`notGenerated`: dynamic slots, `RenderFragment<T>` templates, CSS properties) are skipped in the builder with the same reason in the manifest. Output: one `.cs` per element, CRLF, gitignored with the rest of `Generated/**`, checked by `--check`, listed in `generated.manifest.json`.

### 3.3 Naming rules

| Mapping / API | Builder member |
| --- | --- |
| prop `string` or number | `Name(value)`; the same name as the parameter |
| prop `bool` | `Name(bool v = true)`; `Disabled()` sets it true |
| prop with an enum | `Name(EnumType v)` plus a shortcut per enum member (below) |
| `invert: true` bool (`ShowCloseButton`) | the parameter's own name, same as the component |
| `...Changed` event callbacks | `Bind(...)` (form controls) or `OnNameChanged(...)` |
| `event` / `events` parameters (`OnClick`, `OnClose`) | `OnClick(...)` overloads (Action, Action<T>, Func<Task>, Func<T,Task>, EventCallback) |
| slot parameters | section 3.4 |
| `wrapper` params `ExtraClass`, `AdditionalAttributes` | `Class(...)`, `Attr(...)` on the base |
| a builder alias in the mapping | `"builder": "IconOnly"` on the `Icon` bool param renames the method; a data field, not code |

**Variant values as methods.** `Primary()` for the values of an enum named `Variant`, `Tone`, `Size`, and `Type`-like enums of up to 8 members; `Variant(ButtonVariant.Primary)` always exists. The shortcut is emitted only when its name is unique in that builder (no other enum member, parameter or slot method has it) and not reserved (`Add`, `Set`, `Render`...); the skipped ones are listed in the manifest. Example collisions seen in `button`: `size` has `mini`, `md`, `lg` and `variant` has `plain`, `ghost`, `warn`, `primary`, `secondary`: `Small()` is not a member (the value is `Mini`), so `Mini()`, `Large()` and `Medium()`. Shortcuts for every enum would add roughly one 60-character line per member; the cost is paid in the package size (section 7), so restricting to the `Variant`/`Tone`/`Size` family is Q5.

### 3.4 Slots and children

- default slot (`slot: ""`, `ChildContent`): `Add(...)`, also `Content(...)` as the named alias for symmetry with `Header`.
- named slot `XxxContent` becomes `Xxx(...)` (`ActionsContent` gives `Actions`, `StartContent` gives `Start`); a slot parameter not ending in `Content` keeps its name. Collision with a prop of the same name (a `Heading` prop and a `Heading` slot) keeps the prop and names the slot `HeadingContent(...)`.
- each slot method takes `params IPkNode[]`, `IEnumerable<IPkNode>` and `RenderFragment` overloads; a text slot (mapping `type: string`) takes a `string`.
- a slot rendered by the component as `<span slot=... class="u-contents">` is untouched: the builder passes the `RenderFragment` and the component wraps it, so wrapper markup stays identical.
- children inside a loop: `Add(IEnumerable<IPkNode>)`; `.Key(...)` is `@key`.

### 3.5 Generic and hand-written components

The generic components (`PkTable<TItem>`, `PkDataTable<TItem>`, `PkLookupPicker<...>`, `PkListPage<TItem>` (generated generic: `typeparam` in its mapping) and the other `existing: true` components (`PkFieldGroup`, `PkRecordForm`, `PkSideNav`, `PkAppBarSearch`, `PkGallery`, plus the `mount` category) cannot be derived from the mapping alone, because their interesting parameters (`Load`, `Columns`, `Items`) exist only in their `.razor` source.

- **Generated generic (`typeparam`, today `list-page`)**: fully covered. `PkListPageBuilder<TItem> : PkBuilder<PkListPageBuilder<TItem>, PkListPage<TItem>>`; `Pk.ListPage<TItem>()` is a generic method, `OpenComponent<PkListPage<TItem>>` is a closed type, so no `MakeGenericType` and trimming-safe.
- **Hand-written components (`existing`)**: the generator already reads these files (`load()` greps `@namespace` and `@typeparam`). It also reads their `[Parameter]` declarations by the same regex style (`[Parameter...] public <Type> <Name> { get; set; }`) and emits the builder from them. This keeps builder code generated and costs no hand-written lines; the cost is a regexp over our own source which must be pinned by tests (a malformed declaration fails the generator, naming the file).
- **Bounded exceptions** (what the generator will **not** cover, listed in the manifest and the docs, each reaches the same tree through `Pk.Of<T>().Set(...)`): `PkDevTools`, `PkDevToolsPage`, `PkToolDock`, `PkToolDockPanel` (`blazorOnly`, `mount`), `PkStyles`, `PkGallery` (they are app plumbing, not UI you compose), and any hand-written parameter whose type the regex cannot read (a tuple, a local delegate). Target: **at most 4 exceptions**; the list is a generator constant that may only shrink, same rule as the Blazor baselines.

### 3.6 `Pk.Of<TComponent>()`: Microsoft components and anything else

`Pk.Of<EditForm>().Set(nameof(EditForm.Model), m)` is the generic builder: it is the base class with no generated methods. It exists so the examples above can use `EditForm`, `ValidationSummary`, `InputFile`, `CascadingValue`, and so that a hand-written component (including ones the generator skips) joins a tree. It is untyped on purpose; typed wrappers for Microsoft components are a non-goal.

## 4. Typed enums and a typed icon list

**Enums exist already.** The generator writes 31 enums (`PkGeneratedEnums.cs`: `ButtonVariant`, `ButtonSize`, ...) from the element metadata; the builders reuse them, so a value is checked at compile time and a new value in core appears after the next generation, in both APIs. Gaps that are mapping work, not builder work: parameters still typed `string` in the mappings although the API says `enum` (for example `PkCard.Tone`, `PkIcon.Size`); an audit script should list them (follow-up issue, and each fix is a mapping edit that makes both APIs typed at once).

**Icons.** `core/icons/src/*.svg` is the source of truth (66 icons today: `arrow-left`, `bell`, `save`, `trash`...), `core/icons.svg` is the generated sprite. Proposed: the generator also writes `PkIcons.g.cs`:

```csharp
public static class PkIcons
{
    public const string Save = "save";
    public const string ArrowLeft = "arrow-left";
    ...
}
```

`const string`, not an enum: `IconName` is a string today, an app may add its own sprite, and a constant is inlined by the compiler so unused icons cost nothing at run time or in the trimmed app. Razor benefits unchanged: `<PkButton IconName="@PkIcons.Save" />`. Name rule: `pascal(file name)` (`arrow-left` gives `ArrowLeft`); a digit start is prefixed `V` (the `memberName` rule already in the generator). Input: the generator reads `core/icons/src`, so a new icon appears in `PkIcons` after the bootstrap; a test compares the list with the directory. Alternative (Q6): an `enum PkIcon` plus `IconName(PkIcon)`; rejected as the default because it forces a second overload on every icon-taking parameter and a switch to the string.

## 5. Reusing the components, so behaviour stays 1:1

- The builder **never renders markup**. It opens the generated component with its parameters. `PkElementBase` (runtime initialisation, `Splat`, `Css`, `AdditionalAttributes`), the attribute rendering (`PkAttr.Num`, `Json`, `ToAttr`), `PkCallbackSlot` (every callback parameter of an element, `Load`, `Run`, `Save`) and `PkFormControlBase` (`EditContext`, `NotifyFieldChanged`, `invalid`) all run unchanged because the component is the thing that renders.
- Parameters are set through `AddComponentParameter` by their C# name, so default values, `EditorRequired` analysis (not enforced at run time), and cascading values behave as they do for Razor-compiled trees.
- Events: the builder builds an ordinary `EventCallback` and the component's own handler (`HandleXxx`) invokes it. The `pk-*` events are registered by the existing `EventHandlers` class and the module initialiser; unchanged.
- `Attr("data-x", ...)` and `Class(...)` go through `AdditionalAttributes`, which `PkElementBase.Css`/`Merge` already treat (inline `on...` strings are dropped for the CSP, as for Razor).

Consequence: **a fix in a component or in core reaches the builder with no change**, and a future generator feature (for example a new `model` option) needs its builder rule written once in `renderBuilder` next to the component rule.

## 6. Tests

1. **Generator fixtures** (`scripts/tests/generate-blazor.test.mjs`, 511 lines today, same style): `renderBuilder` for a fixture model: a plain prop, a bool, an enum (with shortcut and collision), a slot (`XxxContent` to `Xxx`), an event with `Action`/`Func<Task>` overloads, a form control (`Bind`), a `typeparam` element, a skipped parameter. Also: a hand-written component's `[Parameter]` regex (incl. a malformed one failing with the file name), `PkIcons` names and the folder comparison, and `--check` covering the new files.
2. **Parity test (bUnit)**, in `blazor/tests/PlainKit.Blazor.Tests`: for **every** generated component (enumerated from `generated.manifest.json`, the same way the existing tests enumerate), render `Render<PkX>(parameters)` and `Render(Pk.X().<same parameters>.Render())` and compare `Markup` after normalising ids. To keep the test itself generated rather than hand-written, the generator emits `BuilderParityData.g.cs` (a table of one sample parameter set per component, from each prop's first enum value, a string, a bool, one slot and one event) so a new component is covered the day it appears. A component without a builder fails the test with a FIX line.
3. **Behaviour**: a small hand-written test file with four cases: callback invoked and receiver re-rendered; `Bind` marks the field modified in an `EditForm`; a slot with a loop and `Key`; `Pk.Of<EditForm>`.
4. **Trimming and AOT**: a `blazor/tests/TrimCheck` console/library project `PublishTrimmed=true`, `TrimMode=full`, `EnableTrimAnalyzer=true`, `IsAotCompatible=true` referencing the package and using three builders; the test is that publishing produces **no IL2xxx/IL3xxx warnings** and that an app referencing no builder links away every `*Builder` type (check with `ILLink` size diff or by asserting the type is absent from the trimmed assembly). This is a CI job in the `dotnet` group of `scripts/verify.mjs` (a new check with a `FIX:` line, in the `CHECKS` table, so the generated docs table stays in sync).

## 7. Documentation, skills and package size

**Docs and skills (part of done for every PR in the split):**

- `scripts/skills/plainkit-blazor/SKILL.md` is 217 lines in the repo today; the owner states the 250-line cap, so the builder goes into `scripts/skills/plainkit-blazor/references/fluent-builder.md` (the API, the 8 examples, `Render`, `Bind`, the naming rules, the exception list) and SKILL.md gets **at most 6 lines**: when to choose the builder (data-driven or library code), and a link. The workflows section gains one workflow, "Build a UI from C# code".
- The gallery samples (`core/site`) are Razor-less web pages; a Blazor sample page (the existing samples) gets one builder-based sample. The README section "Using the skills" is unchanged; the Blazor README gets a short section.
- Per-element docs: the generator writes `<summary>` XML docs on each builder method from the same text as the parameter, so IntelliSense is identical.
- Changelog: one `added` fragment per code PR.

**Package size.** The estimate is deliberately rough and to be measured in PR 3 against the actual assembly: the 117 components are 285 KB of `.razor` source today (`Generated/*.razor`). A builder per component is about 60 to 100 lines of expression-bodied one-liners; my estimate is **150 to 250 KB of additional source and a 300 to 500 KB larger `PlainKit.Blazor.dll` before compression** (about 100 KB in the `.nupkg`), mostly the overloads of events and slots (5 overloads per event). Mitigations to try, in order: fewer event overloads (`Action`, `Func<T,Task>`, `EventCallback` only), enum shortcuts only for the `Variant`/`Tone`/`Size` family (Q5), and split the builders into a **second package `PlainKit.Blazor.Builders`** referencing the first (Q1). For an app that does not use a builder the trimmer removes the types; for WASM the download only grows if builders are referenced. The existing size budgets (the page layer, per-element) are about core's JS/CSS and are not touched; a Blazor package size check, if one exists in `scripts/check-package.mjs`, gets the new number measured, not raised silently.

## 8. Risks, delivery, breaking-change status, open questions

### Risks

| Risk | Mitigation |
| --- | --- |
| Hand-written Blazor code (`builder-runtime`, about 130 lines) | Generate the base from the generator (Q2); otherwise a new category, budget set at the measured size, never raised |
| Re-render semantics: events need a receiver | `Render(this)` documented and tested; without it the handler runs but nothing re-renders (the same as an `EventCallback` with a null receiver) |
| Package grows noticeably | Measured in PR 3, fewer overloads, optional second package (Q1) |
| `AddComponentParameter` by name: a parameter renamed in a mapping | `nameof(PkX.Param)` in every generated call turns it into a compile error, caught by `dotnet build` |
| Regex over hand-written components | A pinned fixture test; the exception list is bounded and shrinks |
| Two APIs to document | The builder is documented in one reference file and in IntelliSense; the Razor API stays the default in all docs |
| Tree built every render (allocations) | Builders are cheap objects; fine for pages, and a library can cache a `RenderFragment`; documented, measured once in PR 3 with a bUnit render of 200 nodes |
| Hot reload / Razor tooling cannot see inside a C# chain | Accepted; it is why Razor stays the default |
| Name clashes (`Pk.Button()` vs `PkButton`) | The `Pk` class is generated and reserved; shortcut collisions are skipped and listed |

### Delivery: PRs of about 400 hand-written lines each (generated files do not count)

1. **Generator: model reuse and the base.** `renderBuilder` skeleton (plain props, bools, strings, slots) for the generated components only, plus `PkBuilder` (or its template); generator fixtures; manifest section `builders`. ~350 lines (JS in the generator and its test). No consumer yet: behind the existing `--check`, files generated but unused.
2. **Enums and icons.** Enum shortcuts with collision rules, `PkIcons` from `core/icons/src`, the icons test. ~250 lines. Razor benefits at once (`PkIcons`).
3. **Builders over events, `Bind`, form controls, typeparam elements**, `Pk.Of<T>`; the measured size and allocation numbers go on the issue. ~400 lines.
4. **Hand-written components** (regex of `[Parameter]`), the exception list. ~250 lines.
5. **Parity test** (generated data table), behaviour tests, the trimming/AOT check in `verify.mjs`. ~300 lines.
6. **Docs and skills**: `references/fluent-builder.md`, SKILL.md lines, the sample page, README section, changelog fragments. Docs only.

Each leaves `main` releasable; builders are additive and unused until PR 3 is merged.

### Breaking-change status

Purely additive. No existing component, parameter, namespace or enum changes. The only visible effects: new public types `Pk`, `PkIcons`, `*Builder` in `PlainKit.Blazor` (the `Pk` static class name must not clash with an existing public type: verified no `Pk` type in `blazor/src` is named exactly `Pk`, to be re-checked at PR 1), and a version bump of the API surface baseline in the release PR (minor). An app that already has a type named `Pk` would need an alias, which is one more reason for Q3.
